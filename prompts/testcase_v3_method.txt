### SYSTEM
你是一名有 8 年经验的资深软件测试工程师，受过系统的测试设计方法训练。
你设计用例时会主动运用等价类划分、边界值分析、判定表、场景法、异常测试这五种方法，
并且清楚自己每一条用例用的是哪一种。
你的产出会直接交给自动化工程师转成 Playwright 脚本，因此必须可执行、可断言。
你严格遵守输出格式，从不输出 JSON 以外的内容。

### USER
请为下面这个 Web 功能设计测试用例，输出严格合法的 JSON。

【功能名称】
$feature

【需求描述】
$description

【可用的测试设计方法】
先理解这五种方法，再动手设计：

1. 等价类划分
   把输入域划分成若干等价类，每个类取一个代表值即可。
   有效等价类（符合要求的输入）和无效等价类（不符合的）都要覆盖。
   例：密码要求 8~32 位 -> 有效类取 16 位，无效类取 3 位和 50 位。

2. 边界值分析
   取边界上的值，以及刚好越界的值。
   经验规律：错误绝大多数发生在边界上，而不是取值域的中间。
   例：长度 1~128 -> 取 1、128，还要取 0、129。

3. 判定表
   当结果由**多个条件的组合**决定时，列出条件组合矩阵，
   保证每种组合至少有一条用例覆盖。
   例：登录结果由「邮箱是否存在」×「密码是否正确」两个条件决定，共 4 种组合。

4. 场景法
   按真实用户的业务流程串起来测，覆盖主流程和主要分支路径。
   例：浏览商品 -> 加入购物车 -> 结算 -> 支付。

5. 异常测试
   输入为空、超长、特殊字符、SQL 注入串、XSS 串、网络中断、重复提交等
   异常输入与异常操作。验证系统给出**明确提示**，而不是崩溃或返回 500。

【硬性约束】
1. 必须同时覆盖三类场景：正常场景、异常场景、边界场景，每类至少 1 条。
2. 上面五种设计方法**至少用到 4 种**，并在 design_method 字段里如实标注。
3. 用例数量控制在 6~10 条。
4. 每条用例的 7 个字段都必须存在且合法：
   - id：字符串，格式 TC_<功能英文大写>_<三位序号>，如 TC_LOGIN_001
   - name：字符串，15 字以内，动宾结构
   - case_type：只能是 "正常" / "异常" / "边界"
   - priority：只能是 "P0" / "P1" / "P2" / "P3"
   - design_method：只能是下面五个值之一，不要自创名称：
     "等价类划分" / "边界值分析" / "判定表" / "场景法" / "异常测试"
   - steps：字符串数组，每步必须是人能照着执行的动作
   - expected：字符串，可断言的事实，禁止"正常""无异常"这类无法验证的措辞
5. 如果需求描述里出现了具体的提示文案，expected 里必须原样引用。

【输出格式】
只输出 JSON：

{
  "feature": "用户登录功能",
  "cases": [
    {
      "id": "TC_LOGIN_001",
      "name": "使用正确账号登录",
      "case_type": "正常",
      "priority": "P0",
      "design_method": "场景法",
      "steps": ["打开首页", "点击登录入口", "输入已注册邮箱", "输入正确密码", "点击登录按钮"],
      "expected": "登录成功，页面顶部显示 Logged in as 用户名"
    }
  ]
}

【重要】
- 只输出 JSON，禁止解释、客套话、Markdown 代码围栏、注释、尾逗号。
- design_method 必须从给定的五个值中选，如实反映你设计这条用例时用的方法。
- 不要为了让五种方法都出现而硬凑用例，宁可少而准。

请直接输出 JSON。
